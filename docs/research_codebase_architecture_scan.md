# Codebase Architecture Scan

## Executive Summary
`pahang-cli` is organized as a menu-driven Python CLI with a single console entrypoint, a thin workflow service, and a set of domain packages for testsheet parsing, Excel workbook updates, and document generation. The broad shape is workable, but the code still mixes presentation, discovery, validation, transformation, and filesystem mutation inside the same modules. The strongest seams already exist as stage classes and repository/storage abstractions; the next step is to make those seams explicit module boundaries instead of letting orchestration classes own too much behavior.

## Current Source And Test Layout
- Runtime entrypoints are split between `start_cli.bat`, the console script in `pyproject.toml`, `main.py`, and `src/workflow_cli.py`. The batch file launches `uv run --frozen pahang-cli` after update checks, the package exposes `pahang-cli = "src.workflow_cli:run_cli"`, and `main.py` simply calls `run_cli()` under `__main__` (`start_cli.bat:21`, `pyproject.toml:19`, `main.py:13`).
- The source tree is organized by domain and workflow area: `src/project`, `src/testsheet`, `src/master`, `src/msms`, `src/quick_report`, `src/whatsapp`, and `src/workflows`. That layout is mirrored in the tests, which are grouped by module/workflow rather than by feature slice, for example `tests/test_testsheet_extractor.py`, `tests/test_populate_total_pe_workflow.py`, `tests/test_raw_material_workflow.py`, `tests/test_quick_report.py`, `tests/test_update_qr02_cba_workflow.py`, `tests/test_whatsapp_report.py`, and `tests/test_cli_menu.py` (`tests/test_testsheet_extractor.py:10`, `tests/test_populate_total_pe_workflow.py:10`, `tests/test_raw_material_workflow.py:9`, `tests/test_quick_report.py:10`, `tests/test_update_qr02_cba_workflow.py:10`, `tests/test_whatsapp_report.py:10`, `tests/test_cli_menu.py:6`).
- The tests are already telling the same story as the code: there are separate suites for parsing, repositories, orchestration, and CLI routing, which is a good sign that the current module boundaries are visible enough to test, even if the orchestration layers are still fat.

## Current Data Flow And CLI Entry Points
- `run_cli()` in `src/workflow_cli.py` is the actual interactive shell. It prints the banner, handles `--help` and `--version`, creates a `CliSession`, loads project and utility actions, and then loops through menu selections until exit (`src/workflow_cli.py:17`, `src/workflow_cli.py:37`, `src/workflow_cli.py:43`).
- Menu rendering is split into `src/cli_menu.py` and `src/cli_selectors.py`. `cli_menu` builds semantic menu items and delegates to `cli_selectors.select_one()`, so the CLI layer controls both the labels and the navigation values (`src/cli_menu.py:44`, `src/cli_menu.py:60`, `src/cli_menu.py:75`).
- Project-scoped actions flow through `src/project_workflow_actions.py`: the action objects gather user input, build workflow requests, call `WorkflowService`, and print the result summary. Utility actions do the same for standalone operations in `src/utility_actions.py` (`src/project_workflow_actions.py:62`, `src/project_workflow_actions.py:104`, `src/project_workflow_actions.py:183`, `src/utility_actions.py:29`, `src/utility_actions.py:109`, `src/utility_actions.py:167`).
- `WorkflowService` is a thin application layer that delegates to concrete workflow classes such as `PopulateTotalPeWorkflow`, `RawMaterialWorkflow`, `QuickReportWorkflow`, `WhatsAppReportWorkflow`, `UpdateQr02CbaWorkflow`, and the MSMS update function (`src/workflows/service.py:26`, `src/workflows/service.py:29`, `src/workflows/service.py:37`, `src/workflows/service.py:45`, `src/workflows/service.py:54`, `src/workflows/service.py:69`, `src/workflows/service.py:63`, `src/workflows/service.py:78`).
- The main user-facing data paths are:
  - testsheet -> TOTAL PE via `populate_total_pe.py`
  - testsheet -> raw material folders via `raw_material.py`
  - testsheet -> QR02 CBA workbook via `update_qr02_cba.py`
  - testsheet -> docx quick report via `quick_report/composer.py`
  - quick report -> WhatsApp report via `whatsapp.py`
  - ENGR/MSMS -> TOTAL PE via `update_data_msms.py` and `master/total_pe.py` (`src/workflows/populate_total_pe.py:199`, `src/workflows/raw_material.py:505`, `src/workflows/update_qr02_cba.py:346`, `src/quick_report/composer.py:37`, `src/workflows/whatsapp.py:292`, `src/workflows/update_data_msms.py:74`, `src/master/total_pe.py:75`).

## Where Responsibilities Are Mixed
- `src/workflows/populate_total_pe.py` is the clearest example of an ETL-style module that still owns too much. It has preflight validation, package discovery, filtering, transformation plan construction, workbook loading, and audit/history recording in one file, even though the file does at least separate those phases into classes (`src/workflows/populate_total_pe.py:23`, `src/workflows/populate_total_pe.py:60`, `src/workflows/populate_total_pe.py:80`, `src/workflows/populate_total_pe.py:146`, `src/workflows/populate_total_pe.py:156`, `src/workflows/populate_total_pe.py:169`, `src/workflows/populate_total_pe.py:199`).
- `src/workflows/raw_material.py` is even more mixed. It validates prerequisites, discovers packages, reads workbook data, checks alignment against TOTAL PE, filters photos, resolves destination paths, creates directories, copies files, and returns result telemetry from the same module (`src/workflows/raw_material.py:64`, `src/workflows/raw_material.py:114`, `src/workflows/raw_material.py:237`, `src/workflows/raw_material.py:383`, `src/workflows/raw_material.py:452`, `src/workflows/raw_material.py:474`, `src/workflows/raw_material.py:505`).
- `src/workflows/update_qr02_cba.py` follows the same pattern: preflight guard, extractor, filter, transformer, loader, auditor, and the top-level workflow all live together. That makes the module easy to trace but hard to evolve without touching multiple stages at once (`src/workflows/update_qr02_cba.py:72`, `src/workflows/update_qr02_cba.py:94`, `src/workflows/update_qr02_cba.py:146`, `src/workflows/update_qr02_cba.py:207`, `src/workflows/update_qr02_cba.py:263`, `src/workflows/update_qr02_cba.py:317`, `src/workflows/update_qr02_cba.py:346`).
- `src/workflows/whatsapp.py` has the same shape: preflight validation, raw extraction, target filtering, transformation, docx rendering, and audit logic are all in one module. The stage separation is useful, but the module still owns both data interpretation and output file creation (`src/workflows/whatsapp.py:72`, `src/workflows/whatsapp.py:110`, `src/workflows/whatsapp.py:146`, `src/workflows/whatsapp.py:217`, `src/workflows/whatsapp.py:261`, `src/workflows/whatsapp.py:277`, `src/workflows/whatsapp.py:292`).
- `src/quick_report/composer.py` is the most coupled report-generation module. It discovers testsheet packages, selects packages by folder or functional location, resolves templates, builds the page list, manipulates docx XML directly for borders, calls multiple render helpers, and composes the final document. That is a lot of orchestration plus low-level output behavior in one place (`src/quick_report/composer.py:37`, `src/quick_report/composer.py:47`, `src/quick_report/composer.py:87`, `src/quick_report/composer.py:113`, `src/quick_report/composer.py:164`, `src/quick_report/composer.py:266`, `src/quick_report/composer.py:341`).
- `src/master/total_pe.py` is nominally a repository, but it also contains sorting, ghost-formatting cleanup, row-upsert heuristics, and an Excel-to-Excel update pipeline. That makes it more than a persistence adapter; it is carrying domain rules and workbook mutation policy together (`src/master/total_pe.py:75`, `src/master/total_pe.py:111`, `src/master/total_pe.py:162`, `src/master/total_pe.py:195`, `src/master/total_pe.py:304`).
- `src/workflows/update_data_msms.py` is an especially leaky bridge: it loads ENGR files, updates MSMS, reloads the workbook, and then updates TOTAL PE in the same function. There is no intermediate plan object or dedicated seam between the two workbook updates (`src/workflows/update_data_msms.py:25`, `src/workflows/update_data_msms.py:58`, `src/workflows/update_data_msms.py:74`).

## Shallow Modules And Leaky Interfaces
- `ProjectEnvironment` is a broad façade over metadata plus workspace storage. It exposes many convenience getters, template resolution helpers, and a WhatsApp resource builder, which is useful for callers but also means the environment object is doing path resolution and domain-specific wiring instead of staying narrowly focused (`src/project/environment.py:13`, `src/project/environment.py:30`, `src/project/environment.py:58`, `src/project/environment.py:94`, `src/project/environment.py:100`, `src/project/environment.py:111`, `src/project/environment.py:146`, `src/project/environment.py:217`).
- `LocalWorkspaceStorage` knows the project directory layout, template resolution, and bootstrap seeding. It creates workspace folders, validates paths, resolves template files, and copies seed assets from the global package templates directory, so it is both a storage adapter and a workspace initializer (`src/project/storage.py:123`, `src/project/storage.py:167`, `src/project/storage.py:181`, `src/project/storage.py:251`, `src/project/storage.py:280`).
- `config.py` hardcodes the package-level template directory, template names, seed files, and ENGR workbook patterns. That makes path resolution depend on global package state, which leaks into `LocalWorkspaceStorage` and makes project-root isolation harder to reason about (`config.py:26`, `config.py:29`, `config.py:57`, `config.py:82`).
- `RawMaterialRequest` carries both `output_path` and `target_dir`, which creates a small but real interface ambiguity. The workflow reads both fields interchangeably during validation and extraction, so the request object is signaling two concepts that appear to be the same operational target (`src/workflows/models.py:49`, `src/workflows/raw_material.py:69`, `src/workflows/raw_material.py:129`).
- `ProgressSink` is typed as a variadic callable, and the CLI actions pass ad hoc lambdas or helper functions into workflow requests. That keeps reporting flexible, but it is also a loose interface that hides what progress messages are expected or how they should be consumed (`src/workflows/models.py:14`, `src/project_workflow_actions.py:24`, `src/utility_actions.py:55`).

## Testability Pain Points
- The CLI action layer is highly interactive and therefore requires patch-heavy tests. `tests/test_cli_menu.py` mostly verifies routing and menu item construction rather than real execution, which is expected but also shows that most logic is buried behind console selection helpers (`tests/test_cli_menu.py:11`, `tests/test_cli_menu.py:46`).
- `tests/test_utility_actions.py` only checks registry shape and factory callability, which is another sign that the real behavior lives behind interactive or filesystem-bound runners (`tests/test_utility_actions.py:4`).
- The workflow modules instantiate concrete repositories and workbooks directly in many places. That keeps the production path straightforward, but it makes isolated tests rely on monkeypatching or temp directories instead of being able to swap in narrow interfaces cleanly (`src/workflows/populate_total_pe.py:68`, `src/workflows/raw_material.py:122`, `src/workflows/update_qr02_cba.py:105`, `src/workflows/whatsapp.py:308`, `src/master/total_pe.py:75`).
- `src/quick_report/composer.py` imports optional COM support at module import time and falls back conditionally. That means the module’s behavior changes with platform and installed packages, which raises the cost of deterministic unit tests on non-Windows environments (`src/quick_report/composer.py:13`).
- `src/project/environment.py:get_or_create_utility_environment()` searches upward from a target directory to infer a project root and also prompts the user when no target is provided. That is convenient for operators, but it makes utility workflows harder to test because the environment can be synthesized from current state instead of injected explicitly (`src/project/environment.py:217`).

## Architecture Improvement Options
1. Split the current “workflow” modules into explicit layers: `extractor`, `validator`, `transformer`, `loader`, and `auditor`, with the top-level module acting only as the application orchestration module. `populate_total_pe.py`, `raw_material.py`, `update_qr02_cba.py`, and `whatsapp.py` already hint at this shape; the next step is to move those stages into separate modules so each seam has one responsibility (`src/workflows/populate_total_pe.py:23`, `src/workflows/raw_material.py:64`, `src/workflows/update_qr02_cba.py:72`, `src/workflows/whatsapp.py:72`).
2. Introduce narrow interfaces for the external world: a `TestsheetSource` interface, a `WorkbookRepository` interface, a `ReportRenderer` interface, and a `ProjectWorkspace` interface. The current code already has repository abstractions, but they are mixed with concrete Excel/docx behavior, so these interfaces would give the workflows a cleaner adapter boundary (`src/testsheet/repository.py:13`, `src/master/total_pe.py:45`, `src/project/storage.py:46`).
3. Move filesystem path resolution into one workspace module and keep domain modules path-agnostic. `LocalWorkspaceStorage`, `ProjectEnvironment`, and `config.py` currently share that responsibility, which makes the seams blurry and causes path policy to leak into the workflows (`src/project/storage.py:123`, `src/project/environment.py:13`, `config.py:26`).
4. Treat the CLI action classes as presentation adapters only. They should gather user intent, build request objects, and hand off to an application service; the service should not depend on menu concepts or printing policy. `project_workflow_actions.py` and `utility_actions.py` are already close to that boundary, so this is a refactor of shape rather than a redesign (`src/project_workflow_actions.py:29`, `src/utility_actions.py:9`).
5. Make the tests follow the seams rather than the modules when practical. Right now the suite is already split by module, but the biggest return would come from tests that pin the extractor/transformer/loader interfaces independently, so workflow regression tests can stay thin and focused (`tests/test_populate_total_pe_components.py:1`, `tests/test_raw_material_components.py:1`, `tests/test_quick_report_components.py:1`, `tests/test_update_qr02_cba_components.py:1`, `tests/test_whatsapp_report_components.py:1`).

## Bottom Line
The repo already has the right vocabulary in place: modules, repositories, environments, workflow services, and stage classes. The main architectural issue is not missing structure so much as misplaced structure. Presentation adapters still own orchestration, repositories still own workbook policy, and some workflow modules still combine validation, extraction, transformation, and output. The cleanest next move is to sharpen the existing seams into explicit module boundaries and keep adapters thin.
